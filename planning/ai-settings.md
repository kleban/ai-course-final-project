# Налаштування AI, економія запитів і використання токенів

Дата: 2026-10-10 (Europe/Kiev). Підстава: уточнення автора, історія 013. Це вимоги й технічна пропозиція для MVP; реалізацію не розпочато.

## Вимоги автора

- Різні моделі для різних задач; вибір у налаштуваннях системи.
- Введення ключа OpenAI через систему та захищене зберігання в зашифрованому вигляді.
- Відстежувати використання токенів. Грошовий облік, тарифи, рахунки й оцінку вартості в MVP не включати: автор прямо відмовився від цього після початкової згадки витрат.
- Зменшувати зайві AI-виклики, зберігаючи перевірюваність результатів.

## Розподіл задач — пропозиція агента

| Тип задачі | Перший кандидат | Пояснення |
| --- | --- | --- |
| Звичайна робота агента з обмеженим каталогом інструментів | gpt-6-luna | Економний початковий профіль; перевірити правильність викликів і якість українських пояснень |
| Короткі пояснення розрахунків і текстовий підсумок | gpt-6-luna | Задача спирається на вже обчислені факти, не потребує повторного аналізу |
| Складне планування, неоднозначне зіставлення даних | gpt-6.1-sol | Сильніший профіль, обраний явно; неоднозначні перетворення все одно уточнюються з користувачем |
| Векторні представлення для RAG | text-embedding-3-small | Спеціалізована embedding-модель; не генерує відповіді |
| Статистика, пропуски, з’єднання, регресія, матриці й графіки | Без LLM | pandas/NumPy/statsmodels/Plotly виконують розрахунок локально |

Це стартові кандидати, не затверджені моделі. За [актуальним каталогом OpenAI](https://developers.openai.com/api/docs/models), Luna орієнтована на економні масові задачі, Sol — баланс можливостей і вартості. Кандидати підтримують function calling за своїми офіційними сторінками: [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol). [Embedding-модель](https://developers.openai.com/api/docs/models/text-embedding-3-small) обирається окремо. Доступ у конкретному обліковому записі й придатність для наших даних ще не перевірено. Моделі не називаємо mini/nano за аналогією без перевірки офіційного каталогу.

## Екран «Налаштування AI»

Пропозиція: налаштування спільні для локального MVP; проєктні перевизначення до першого обсягу не додавати.

- Стан ключа: не налаштовано / збережено / перевірено / помилка. Поле введення приховане; після збереження ключ не повертається в UI. Дії: зберегти, замінити, видалити, перевірити доступ. Перевірка не запускає довільний платний аналіз автоматично; якщо потрібна генерація, показати це перед запуском.
- Таблиця «Задача → модель». Користувач обирає модель із переліку кандидатів; розширений режим дозволяє ввести перевірений model ID. Наявність ID у каталозі акаунта не доводить підтримку всіх параметрів — capabilities перевіряти окремо.
- Параметри профілю: модель, підтримуваний reasoning effort, межа вихідних токенів, межа контексту, ліміт кроків агента, ліміт повторів. Не показувати параметри, які модель не підтримує.
- Збереження конфігурації в SQLite без ключа. Майбутні запуски використовують нову конфігурацію; поточний має її незмінний знімок. У trace видно тип задачі, обрану й фактично використану модель, версію конфігурації.
- Підвищення до сильнішої моделі — явний вибір або окремо погоджене правило. Немає прихованого автоматичного переходу після кожної помилки. Відсутність доступу не запускає іншу модель мовчки.

## Захищене зберігання ключа — пропозиція для Windows (не обрано)

Рекомендація: backend використовує Python `keyring` з перевіреним системним Windows backend. Ключ потрапляє у сховище облікових даних Windows, а в нашій БД лишається лише ідентифікатор запису. ОС забезпечує захист збереженого секрету; власного пароля шифрування поруч із ключем не створюємо. Джерела: [keyring](https://keyring.readthedocs.io/en/latest/), [Microsoft CredWrite](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew), [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

Важлива властивість: це захист у контексті облікового запису Windows, не ізоляція від усіх інших процесів цього користувача. Підтримуваний захищений backend перевіряється при запуску; незашифрованого файлового fallback немає. За помилки збереження UI повідомляє про невдачу; ключ не потрапляє у журнали, конфігурацію або експорт.

**Потребує дозволу автора перед реалізацією:** системне сховище фізично перебуває поза репозиторієм. AGENTS.md вимагає всі матеріали тримати в проєкті й узгоджувати неминучий зовнішній запис; водночас забороняє секрети в репозиторії. Пропонується вузький виняток лише для ключа OpenAI в захищеному сховищі Windows. Документація, моделі налаштувань, журнали та інші результати залишаються в проєкті. Сховище зараз не створювали й ключ не запитували. Якщо виняток не погоджено, тимчасова альтернатива — ключ лише на час сесії без збереження.

## Токени в трасуванні

За фактичним `usage` API зберігати в кожному запиті: `input_tokens`, `output_tokens`, `total_tokens`; доступні деталізації `cached_tokens`, `cache_write_tokens`, `reasoning_tokens` — окремо. Поля можуть бути відсутні; тоді позначати «невідомо», не нуль. Зберігати вихідну структуру usage для перевірки. Джерело: [Responses API](https://developers.openai.com/api/reference/python/resources/responses/methods/create).

Cached tokens — підмножина вхідних, reasoning tokens — підмножина вихідних; не додавати їх ще раз до total. Окремі embedding-запити мають власне usage; їх показувати як embedding-токени, не як текстову відповідь агента. Для streaming завершений usage враховувати один раз. Повторні реальні спроби обліковувати окремо; якщо usage не отримано після помилки, не оцінювати його як відомий нуль.

UI: коротке використання в деталях кроку; підсумок запуску й фільтри за моделлю, типом задачі та проєктом на екрані трасування. У підсумку окремо показати відомі токени та число викликів із невідомим usage. Немає грошових показників, тарифного довідника чи billing dashboard. Загальний лічильник токенів не обіцяє точну суму рахунку OpenAI.

## Як економимо

1. Кнопки статистики й графіків викликають локальні функції напряму; AI-пояснення — за потребою.
2. Модель отримує опис полів, компактні результати й вибрані приклади, а не весь датасет або всю історію trace. Обмеження контексту не приховують важливих умов задачі.
3. RAG додає лише релевантні перевірені фрагменти. Embeddings незмінених фрагментів повторно не генеруються; ключ кешу включає текст, модель і розмірність. Зміна embedding-моделі запускає явне переіндексування, не змішування несумісних векторів.
4. Розрахунки та відповіді можна повторно використати за збігом проєкту, версії даних, задачі, параметрів, моделі й версії методичних джерел. Кешований результат позначений; новий виклик OpenAI не симулюється.
5. Вихідні токени, кроки й повтори обмежені; при досягненні ліміту агент зупиняється зі зрозумілим станом. Max output охоплює також reasoning-токени для відповідних моделей.
6. Стабільну частину інструкцій розміщувати перед змінним контекстом для можливого [prompt caching OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching). Це окремо від нашого кешу результатів; спрацювання перевіряється за usage, не гарантується.

Перш ніж затвердити профілі, порівняти кандидати на одному контрольному наборі задач: правильність інструментів, відсутність вигаданих чисел, якість пояснення, токени й тривалість. Економія не доведена самим вибором моделі; експерименти ще не виконано.

## Локальний пошук RAG — пропозиція після запитання автора, історія 014

Автор запитав про можливість локального RAG без оплати пошуку. Рекомендація агента для малого корпусу правил: локальні багатомовні embeddings через Sentence Transformers, фрагменти й метадані в SQLite, пошук схожості через NumPy. Ваги та кеш моделі розміщувати всередині репозиторію. Навчання моделі з нуля й окремий сервер векторної БД не потрібні для цього варіанта; модель, швидкість на CPU та якість українського пошуку перевірити прототипом. Ще простіша альтернатива — SQLite FTS5 для пошуку слів, але вона слабше покриває перефразування та міжмовні запити.

Так локальна підготовка векторів і пошук не викликають платний API; залишаються ресурси комп’ютера та початкове завантаження залежностей/ваг. Генерація відповіді зовнішнім OpenAI лишається платною, а знайдені фрагменти входять у її вхідні токени. Перегляд знайдених джерел може працювати без генерації. У trace розрізняти локальний пошук (без usage OpenAI) і зовнішню генерацію (фактичний usage). Раніше запропонований text-embedding-3-small лишається альтернативою, не затвердженим рішенням; локальний варіант теж ще не затверджено.

Джерела: [Sentence Transformers semantic search](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html), [SQLite FTS5](https://www.sqlite.org/fts5.html). Документацію прочитано, нічого не встановлювали й не завантажували.

## Реалізовано: сторінка «Моделі AI» (069, D-77)

`Налаштування → Моделі AI`: 13 задач за етапами пайплайну (проєкт і дані, оглядовий аналіз, підготовка, модель і перевірка, висновки та звіт, база знань), для кожної — модель OpenAI (gpt-6-luna, gpt-6.1-sol, text-embedding-3-small для пошуку) або «Без OpenAI». Ліміти: вихідні токени, кроки агента. Збереження в SQLite `ai_configuration` (v13) без ключа, події `ai.configuration.saved/reset`. Стан ключа читається з `.env` і показується замаскованим (`sk-…1234`); поле «Замінити ключ» навмисно не передає значення на сервер. Ключі задач (`model_for(task)`) — контракт для майбутнього адаптера й помічника. Виклики OpenAI ще не реалізовані; доступ моделей не перевірявся.

## Реалізовано: адаптер викликів OpenAI (071)

`openai_client.py`: Responses API (`POST /v1/responses`, `store=false`) через httpx без нового пакета; модель береться з налаштування задачі, ліміт вихідних токенів — з налаштувань. Без автоматичних повторів і без тихого переходу на іншу модель. Помилки 401/403/404/429/5xx, тайм-аут і відсутність мережі пояснюються українською. «Перевірити доступ» — безкоштовний `GET /v1/models/{id}` для кожної обраної текстової моделі; «Пробний запит» — один платний запит до 256 вихідних токенів лише за кліком. Журнал `ai_calls` (схема v14): задача, модель, проєкт, запит без ключа (скорочений >4000 символів), відповідь, фактичне usage (відсутнє — «невідомо», не 0), помилка, тривалість; підсумок токенів без грошей. Реальний виклик OpenAI не виконувався: у середовищі агента немає ключа й мережі до OpenAI; перевірено на імітації транспорту.

## Повтори й рівні моделей (072, D-79)

За вимогою автора сервіс повноцінно намагається виконати задачу, а не зупиняється після одного запиту.

- **Рівні моделей:** для кожної задачі до 3 рівнів (основна + 2 запасні), обираються на сторінці «Моделі AI». Типово: економна gpt-6-luna → сильніша gpt-6.1-sol; для складних задач навпаки.
- **Повтори:** на кожному рівні до N повторів (типово 2, налаштовується 0–5) при тимчасових збоях: тайм-аут, немає мережі, 429, 5xx. Пауза 1 → 2 → 4 … с (до 20 с) або скільки просить `Retry-After`.
- **Перехід на наступний рівень** без повторів: модель недоступна (403/404), запит відхилено (400), відповідь порожня або обірвана лімітом токенів, або перевірка змісту відхилила відповідь.
- **Зупинка одразу:** немає ключа або ключ відхилено (401) — інші моделі не допоможуть.
- **Журнал:** кожна спроба — окремий запис з однаковим `run_id`: рівень, модель, номер спроби, результат, причина, наступний крок (повтор / наступний рівень / готово / зупинка / вичерпано), пауза, токени. Користувач бачить, якою моделлю й з якої спроби отримано відповідь, і токени всіх спроб.
- **Межа:** не більше 3 рівнів × (1 + N) спроб; якщо все вичерпано — зрозуміле повідомлення з останньою причиною, а не тиха відмова.

Це переглядає попереднє «без повторів і без переходу на іншу модель» (071): перехід тепер явно налаштований користувачем і видимий у журналі, тому не є прихованим. Перевірено на імітації транспорту; реальних викликів ще не було.
