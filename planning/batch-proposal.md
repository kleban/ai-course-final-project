# OpenAI Batch: відкладені AI-чернетки звітів

2026-10-12 (Europe/Kiev), історія 114. **Відхилено автором у 116 (D-105): не реалізовувати.** Пропозиція агента збережена як архів. Автор попросив знайти доречний сценарій Batch для MVP, зокрема відкладений звіт. Пріоритет перебудови DuckDB не змінено.

## Перевірені можливості й поточний код

Офіційне джерело, перевірено 2026-10-12: [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch). Пакет незалежних запитів передається файлом JSONL; підтримується /v1/responses. Вікно виконання — 24 години; не слід обіцяти готовність за кілька хвилин або точно в заданий час. Знижка 50% від синхронного API; інший пул лімітів. Доступність конкретних моделей та ліміти акаунта перевіряти перед реалізацією. В одному вхідному файлі одна модель. Відповіді співставляються за custom_id, не за порядком рядків. Можливі часткові помилки й expired; успішні відповіді в такому пакеті можна отримати окремо.

У сервісі вже є ReportStore.ai_draft (src/data_story/reports.py): один синхронний виклик report_draft за зафіксованими фактами й збереженим snapshot, JSON із п’ятьма розділами, перевірка Markdown та revision. ReportStore.render виконує локальну збірку Quarto; вона не є запитом OpenAI. ConclusionStore.prepare спочатку локально добирає RAG-фрагменти, потім робить один виклик conclusions. Batch-транспорту або реєстру batch-завдань у сервісі наразі немає.

## Рекомендований мінімальний сценарій

В обраного звіту додати вибір «AI-чернетка зараз» / «AI-чернетка відкладено». Сценарій справжнього пакета: кілька незалежних звітів за вже готовими моделями/наборами; один запит на повну чернетку кожного звіту, спільна модель. Не розбивати короткий звіт на багато запитів лише для демонстрації batching: це дублює контекст і може погіршувати узгодженість тексту. Один відкладений запит також можливий, але при малому обсязі користь головно навчальна, а не висока пропускна здатність.

1. Явна дія користувача фіксує snapshot чисел, метаданих, джерел/затверджених висновків і revision. Усі потрібні SQL-обчислення та локальний RAG виконуються до надсилання; числа й графіки не генеруються LLM.
2. Сервіс надсилає готові незалежні запити OpenAI Batch, зберігає batch_id та зіставлення custom_id зі звітом/версією. UI показує «В обробці», «Готово», «Помилка», «Скасовано». Закриття локального сервісу після прийняття пакета OpenAI не має втрачати ідентифікатор; стан і результат перевіряються при наступному запуску або явним оновленням.
3. Результати завантажуються й проходять ту саму перевірку JSON/Markdown, що синхронні чернетки. Якщо автор змінив звіт, пізня відповідь не перезаписує його: окрема чернетка на початковому snapshot. Користувач переглядає й застосовує результат; збірка HTML лишається локальною. Затвердження автора не автоматизується.

SQLite зберігатиме службовий стан завдань/версії/статуси/журнал/фактичні токени. DuckDB — вихідні аналітичні результати. Локальні JSONL і завантажені результати — лише всередині проєкту; секрети не записуються. Грошовий облік у продукт не додається. Потрібні захист від подвійного запуску, відновлення стану після перезапуску, окремі помилки по запитах і повтор лише невдалих задач за явною дією. Це інженерні деталі пропозиції, не прийнятий обсяг.

## Альтернативи та межі

- Відкладені висновки для кількох готових моделей: той самий принцип, з локально підготовленим RAG. Можна другим сценарієм після звітів, якщо погоджено.
- Інженерна оцінка AI: пакет заздалегідь підготовлених контрольних питань із збереженими RAG-фрагментами; перевірка відповідей/джерел після завершення. Природний batch-сценарій, але менш видимий користувачу й містить додаткові критерії оцінки.
- Поточний чат і послідовний агентний цикл не переводити в Batch: наступний інструмент/запит залежить від попередньої відповіді.
- Статистика, моделі й HTML-експорт — локальні обчислення; їхня локальна фонова черга відрізняється від OpenAI Batch. Звичайне відкладене виконання не автоматично означає використання Batch API.
- RAG-embeddings у нас локальні bge-m3, тому OpenAI embedding batches не потрібні без окремого рішення змінити цей підхід.

## Перевірки, якщо автор погодить реалізацію

Підмінений Batch API: різний порядок відповідей/custom_id; одна помилка серед успішних; expired; некоректний JSON; подвійне завантаження результатів; перезапуск із збереженим batch_id; змінений revision; ізоляція проєктів; незмінність початкових чисел; відсутність нових AI-викликів при HTML-експорті. Реальний пакет — окрема погоджена перевірка.

У 114 виконано лише дослідження документації/коду й підготовку пропозиції. Жодних API-викликів, завдань Batch або змін продуктового коду не зроблено.
