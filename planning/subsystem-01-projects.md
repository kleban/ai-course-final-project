# Підсистема 01 — проєкти й локальне збереження

Дата: 2026-10-10 (Europe/Kiev). Автор погодив почати з проєктів і спочатку перевірити ядро, потім додати браузерний екран. Джерело — історія 015. Деталі нижче — технічна специфікація агента для цього обсягу.

## Межі

Створити проєкт, показати список, відкрити проєкт, зберегти його після перезапуску. Проєкт має незалежний UUID, назву, необов’язкову мету та дату створення UTC. Однакові назви дозволені, але не об’єднують записи. Облікових записів, входу, ролей, видалення й архівування немає.

Ядро не містить UI, завантаження даних, AI, RAG або графіків. Воно надає один контракт для майбутніх екранів і API; не дублювати зберігання в UI. Мінімальний журнал створення/відкриття — початок спостережуваності, не завершене наскрізне трасування всіх компонентів.

## Контракт і збереження

`ProjectStore(database)` відкриває SQLite. `create(name, purpose)`, `list_projects()`, `get(id)`, `open(id)`, `events(id)` — функції ядра. Назва після видалення крайових пробілів: 1–120 символів; мета: 0–2000. Це запропоновані ліміти MVP. Невалідні поля дають ValueError, невідомий ID — ProjectNotFound; помилки збереження не приховуються.

Під час створення запис проєкту й подія журналу зберігаються однією транзакцією. Неуспішний запис журналу відкатує створення. Читання не створює подій; явне відкриття створює project.opened. Схема має версію; невідома наявна БД не переписується. У логах лише контрольовані події, без ключа OpenAI чи мережевих заголовків.

Майбутня робоча БД — `runtime/data-story.sqlite3` всередині репозиторію; каталог виключений із Git. Тести працюють виключно з тимчасовими БД у `tmp/tests/`. Runtime не містить секретів. SQLite означає локальне збереження, не окремий сервер.

## Екран цього компонента (реалізовано, історія 017)

Один екран: список проєктів, кнопка «Створити проєкт», поля назви й мети, кнопка «Відкрити». Після відкриття постійно видно поточний проєкт; перемикання очищує стан попереднього проєкту. На цьому етапі не показувати непрацюючу кнопку завантаження; додати її в підсистемі 02. Стиль — адаптація основної лекції.

Реалізовано NiceGUI поверх FastAPI в одному процесі (`web.py`), з HTTP API `/api/projects`, `/api/projects/{id}`, `/api/projects/{id}/open`, `/api/projects/{id}/events` і службовими `/health`, `/shutdown`. UI та API користуються одним `ProjectService`; доменна логіка лише в ядрі. Активний проєкт передається параметром `?project=<id>` у URL, а не зберігається глобально.

## Приймання ядра

1. Порожній старт показує порожній список; українські назва й мета зберігаються після повторного відкриття БД.
2. Однакові назви мають різні ID й незалежні журнали.
3. Невалідні поля, невідомий ID та помилка запису не створюють часткових даних.
4. Назва із SQL-текстом зберігається як текст.
5. Невідома або майбутня схема не змінюється.

Перевірки: `tests/test_projects.py`; запуск подвійним кліком `Check-Projects.cmd` або розробницький запуск `tools/check_projects.py`. Це перевірка ядра, не запуск готового застосунку. UI-приймання окреме: створити два проєкти в браузері, перемикати їх, перезапустити застосунок і відкрити збережені записи.

## Дизайн-ітерація 018 — дашборд

За рішенням автора екран перебудовано як дашборд: верхня панель (логотип Data Story, слоган «Від даних до історії», поточний проєкт, позначка «Локально»), ліва навігація (огляд, список проєктів із кнопкою «+», маршрут етапів MVP 01–10 з позначкою «далі»), робоча область праворуч. Огляд: KPI (кількість проєктів, останній створений, сховище) і таблиця проєктів. Поточний проєкт: KPI (дата, події журналу, ідентифікатор), маршрут дослідження, журнал дій таблицею. Стиль за дашбордом автора: біла тла, палітра F3, без заокруглень і тіней, тонкі лінії замість карток, лінійні SVG-іконки як CSS-маски (`icons.py` → `assets/icons.css`). Етапи в меню — лише план, не кнопки. На вузькому екрані меню відкривається кнопкою ☰.

## Результат приймання (2026-10-10, історія 017)

Етап 01 прийнято. `Check.cmd` на Windows: pip check, ruff, формат, mypy, 21 тест — успішно. Ручний UI-сценарій через `Start.cmd`: створено два проєкти з однаковою назвою (різні ID), порожня назва відхилена без запису, відкриття показує поточний проєкт і журнал. Повторний `Start.cmd` не створив другого сервера; `Stop.cmd` завершив сервер; після нового запуску обидва проєкти й журнал збереглися. Зайнятий чужий порт перевірено лише автотестом.

## Ітерація 019 — тип проєкту та інструкції

Проєкт має `project_type`: `regression` (активний, за замовчуванням), `classification`, `clustering` (неактивні до відповідних етапів). Тип вибирається в діалозі створення через випадаючий список з іконками й не змінюється після створення. Для кожного типу є інструкція-промпт: типовий текст у `src/data_story/instructions/<тип>.md`, змінений — у таблиці `instructions`; «Відновити типову» видаляє зміну. Зміни конфігурації пишуться в `config_events`. Схема БД v2; база v1 оновлюється автоматично, наявні проєкти стають регресійними. API: `GET /api/project-types`, `GET|PUT|DELETE /api/project-types/{type}/instruction`.
