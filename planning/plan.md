## Етап 10 — генерація аналітичних звітів

**Погоджено автором:** окремий етап генерації звітів у плані. **Пропозиція автора:** розглянути Quarto для перетворення Markdown у звіти. Вибір Quarto, HTML/PDF/DOCX, структура звіту та його остаточний обсяг ще не затверджені.

Пропозиція мінімального сценарію: у поточному проєкті обрати збережені результати → створити чернетку звіту → відредагувати Markdown → явно сформувати й відкрити/завантажити локальний звіт. Першим форматом агент пропонує HTML; PDF і DOCX — наступні кандидати, а не обов’язкові формати MVP. Звіт можна складати без нового AI-виклику; AI-редагування пояснень, якщо знадобиться, має бути окремою явною дією з журналом і usage.

Пропонована структура: мета, дані й версії наборів, метод, вибрані таблиці та графіки, пояснення результатів, обмеження, джерела. Числа й графіки надходять із перевірених збережених розрахунків; кожний результат має походження. Авторський текст відділяти від автоматичних пояснень. Текстова чернетка зберігається як Markdown; для Quarto сервіс додає керовану оболонку `.qmd` з налаштуваннями й посиланнями на артефакти. Користувачу не потрібно редагувати службовий YAML.

Quarto — кандидат на локальний інструмент формування документів, а не на заміну NiceGUI чи обчислень pandas/DuckDB. Перший прототип пропонується на готових результатах, без виконуваних Python-блоків у звіті й повторного запуску аналізу. Усі вихідні тексти, шаблони, журнали, ресурси й результати зберігати в цьому репозиторії; робочі звіти — у `runtime/projects/<project_id>/reports/<report_id>/`, тимчасові файли — в `tmp/`. Каталоги створювати при реалізації, не зараз. Спосіб розміщення Quarto та його кешів перевірити перед встановленням відповідно до AGENTS.md.

Критерії готовності для погодження: контрольний звіт має точні числа/підписи й джерела; український текст і формули читаються; графіки відповідають основній лекції; чернетку можна змінити й повторно сформувати; повторне формування не викликає AI та аналіз автоматично; звіти двох проєктів ізольовані; помилка формування видима в інтерфейсі та журналі, попередня версія зберігається. Для HTML перевірити локальні ресурси без інтернету; для PDF/DOCX — окрема перевірка верстки й відмінностей форматів, якщо їх оберемо.

Перед реалізацією: вибрати формати й шаблон; перевірити Quarto на Windows/Python 3.13, запуск із Python без ручних команд і потрібні залежності. Для PDF через LaTeX потрібен TeX-дистрибутив (наприклад TinyTeX); цей спосіб не є автоматично обраним. Технологічні джерела — [нотатки](../notes/technology-sources.md). Реалізація етапу 10 не починалася; поточна робота — вибір Markdown-редактора.

## Реалізований локальний запуск

Один Python-процес: NiceGUI з FastAPI, підсистеми як модулі, SQLite як файл. Попередня пропозиція двох серверів та HTTPX між ними переглянута: для цього MVP вони зайві. Сервер слухає лише 127.0.0.1. Входу, ролей, облікових записів та авторизації немає.

Цільовий `Start.cmd`: подвійний клік → перевірка середовища → запуск сервера → браузер після готовності. Зайнятий порт дає зрозуміле повідомлення; чужий процес не завершуємо. Повторний запуск має розпізнавати наш уже запущений застосунок. Зупинка має завершувати сервер без залишених фонових процесів. Реалізовано в ітерації 017: `Setup.cmd`, `Start.cmd`, `Stop.cmd`, `Check.cmd` і `tools/start.py`; повторний запуск, зупинка й перезапуск перевірені вручну на Windows. Інструкція — README.

Первинна підготовка відрізняється від щоденного запуску. Окремий файл налаштування створюватиме .venv і встановлюватиме зафіксовані залежності; потрібен інтернет. Щоденний запуск не перевстановлює пакети чи модель. Наявний Python 3.13 — кандидат середовища; сумісність UI/ML-залежностей перевірити перед встановленням. Сумісність поточних залежностей Python 3.13 перевірена; майбутні ML/DuckDB-залежності перевірити при додаванні. `Check-Projects.cmd` запускає автоматичні тести без окремого запуску браузерного застосунку.

Усі код, документація, .venv, кеші, ваги моделі, дані, тести й журнали — в одному репозиторії. Runtime, tmp і .venv виключені з Git; ключі відповідно до окремого рішення. Не плутати єдиний репозиторій із необхідністю додавати кожен runtime-файл у Git.

Docker поки не включати: для одного локального процесу він додає встановлення й середовище Windows. Розглянути його, якщо знадобиться однакове розгортання кількох сервісів на різних машинах. Це рекомендація агента, не остаточне рішення автора.

Офіційні підстави: [NiceGUI/FastAPI в одному процесі](https://github.com/zauberzeug/nicegui/blob/main/examples/fastapi/main.py), [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/). Інтегрований запуск перевірено в ітерації 017.

## Реалізований етап 02 — завантаження й огляд даних

Реалізовано за дорученням автора (020), перевірено разом із 02b у 025; формальне приймання попереду. Формати й ліміт — тимчасові значення D-25.

- **Сценарій:** у відкритому проєкті кнопка «Завантажити дані» → вибір файла → набір з’являється у списку наборів цього проєкту → «Переглянути» показує перші рядки, кількість рядків/стовпців, назви й визначені типи стовпців, кількість пропусків.
- **Формати:** CSV (UTF-8/Windows-1251, автороздільник) та XLSX (перший аркуш). Ліміт файла — 20 МБ (пропозиція).
- **Збереження:** оригінал копіюється в `runtime/projects/<project_id>/datasets/<dataset_id>/`, метадані — у SQLite (нова версія схеми з міграцією з версії етапу 01). Подія `dataset.uploaded` у журналі проєкту.
- **Помилки:** порожній/пошкоджений файл, непідтримуваний формат, перевищення ліміту — зрозуміле повідомлення без часткового запису.
- **Ізоляція:** набір видно лише у своєму проєкті; два набори з однаковою назвою файла незалежні.
- **Залежності:** pandas і openpyxl (додати в `requirements.lock`, перевірити `Setup.cmd`).
- **Приймання:** автотести парсингу, помилок, ізоляції й міграції схеми; ручний сценарій у браузері з демонстраційним набором автора та перезапуском.

Потрібні рішення автора: формати, ліміт, демонстраційні дані, чи зберігати оригінали.

Це не блокує ядро проєктів; залежні етапи потребують уточнення. Поточна назва — Data Story. Ітерація 026 актуалізує документи й фіксує їх у Git; 03 не почато.
