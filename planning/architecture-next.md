## Узгоджені залежності

- **DuckDB:** табличні дані, версійні результати статистики, зведення, коефіцієнти, метрики, прогнози, залишки та дані графіків. Навчання й математичні обчислення лишаються в pandas/NumPy/sklearn/SciPy; результати записуються в базу.
- **SQLite:** ідентифікатори проєктів, конфігурації, журнали, метадані й службові ідентифікатори наборів; тексти й затвердження висновків/звітів, редаговані правила бази знань у knowledge_documents. Відповідність сирої таблиці визначає каталог DuckDB за project_id, dataset_id, SHA-256 і профілем парсера. Облікові записи не додаються.
- **RAG → база знань:** KnowledgeStore читає правила з knowledge_documents (SQLite), ділить їх на розділи й шукає через TF-IDF та локальні embeddings. SourceLibrary читає книжки з runtime/knowledge-sources (books.json, chunks.jsonl, vectors.npy); кеш векторів правил — runtime/knowledge-index. Тому зв’язок RAG зі SQLite реальний, але SQLite не містить усього книжкового корпусу або векторів. RAG не читає аналітику через DuckDB. Підтверджені входи: чат Assistant._solve, інструмент search_knowledge і вбудовані висновки ConclusionStore. Походження та сторінки джерел зберігаються.
- **Файли:** оригінали завантажень, збережені моделі/матриці за потреби, готові SVG/HTML/QMD, локальні ресурси RAG і Quarto. DuckDB не має замінювати зображення чи виконувані файли моделей таблицею.
- **AI-помічник — чат:** інтерпретує питання, обирає дозволені інструменти, за потреби складає SQL і пояснює результат.
- **Вбудовані AI-функції:** конкретні кнопки підготовки чернеток, висновків і пояснень. Це не автономна фонова система. Обидва входи використовують спільний клієнт OpenAI, налаштування моделей, журнал і RAG; кожен виклик — явна дія користувача.
- **SQL-інструмент:** сервіс передає LLM лише каталог доступних таблиць поточного проєкту, перевіряє запит і повертає обмежену таблицю. Не слід подавати сирі таблиці іншого проєкту в контекст. Читання без записів, ізоляція таблиць, часові/ресурсні межі потребують окремих перевірок перед підключенням LLM.
- **Графіки:** отримують табличні результати; вибір типу й оформлення підкоряється основній лекції. Новий SQL не створює автоматично підтримку нових типів графіків.
- **Звіти:** збираються зі збереженого знімка, не перераховують аналітику й не повторюють OpenAI під час експорту. Текст автора затверджує автор.

## Порядок робіт

1. **Готово, 111:** `analytics.py`, постійні незмінні версії таблиць, каталог/читання, ізоляція проєктів, явний імпорт перевіреного набору через ProjectService/API. Конструктор не створює базу автоматично. Відсутність бази дає порожній каталог. Це перша підсистема, а не завершена міграція.

   Імпорт цього кроку зберігає розібрану таблицю оригінального файла й враховує метадані у відбитку версії. Авторські коди пропусків, зміни типів і ролей ще не застосовуються новим сховищем як обчислювальні перетворення; чинні модулі роблять це попереднім перевіреним способом. Перед переведенням споживачів треба визначити сире й аналітично нормалізоване подання. Новий API не викликає OpenAI й не приймає SQL.
2. **Готово, 112 (сирі набори):** завантаження, копіювання, підготовка й зведення записують таблицю до завершення службової транзакції; помилка відкочує нову аналітичну таблицю й файли. DatasetStore.frame перевіряє SHA-256 оригіналу навіть при повторному читанні, читає таблицю з DuckDB; попередні набори імпортує ліниво при читанні. Відновлюються типи pandas. Метадані й коди пропусків застосовуються чинними перевіреними функціями після читання; окреме нормалізоване подання для SQL ще потрібне. Після аварійного завершення процесу між двома базами можлива невикористана таблиця DuckDB: її не видають без існуючого набору SQLite; автоматичного видалення старих версій немає.
3. Статистика та числові дані графіків: ключ результату включає версію даних, метаданих, параметри й версію методу. Зміна кодів пропусків/типів/ролей не повинна повертати старий кеш. Оформлення SVG не має змінювати числовий результат.
4. Моделі: зберігати таблиці коефіцієнтів, метрик, прогнозів і залишків з `model_id`, `training_run_id` та походженням. Правило train-only для перетворень та недоторканність тестової вибірки зберігаються.
5. Перевірений SQL-інструмент і обидва входи AI; окремо перевірити заборону зміни даних, доступу до сторонніх файлів і проєктів, надмірних запитів, збереження результатів/помилок. Формування SQL від LLM погоджене; конкретна реалізація валідатора ще попереду.
6. Моніторинг постійної DuckDB, оновлення поточної схеми й перевірка всього сценарію. Потім графіки Seoul і презентація.

## UI, FastAPI та аналітика — уточнення 113

2026-10-12 (Europe/Kiev). Автор попросив розрізнити користувацький UI і FastAPI на схемі та пояснити, чи аналітичні модулі мають окремий сервер. Перевірено фактичний код: web.configure створює один ProjectService, додає HTTP router до nicegui.app і передає той самий сервіс у сторінки NiceGUI. Обробники UI викликають методи ProjectService напряму; маршрути FastAPI викликають ті самі методи. ProjectService звертається до StatisticsStore, ModelStore та інших звичайних Python-модулів, які не піднімають власні FastAPI-сервери. Обчислення — pandas/NumPy/SciPy/sklearn; FastAPI обслуговує HTTP-вхід, не є обчислювальним модулем. Все працює в одному серверному процесі.

Для подальшої схеми: один зовнішній контейнер «Локальний сервіс Data Story», усередині окремі компоненти «UI / NiceGUI», «HTTP API / FastAPI», «Спільний сервіс / ProjectService» та «Аналітичні модулі». UI → ProjectService і HTTP API → ProjectService → аналітика → сховища; не малювати обов’язковий UI → HTTP API або окремий сервер на кожний аналітичний модуль. Це логічний поділ чинного коду, не запит на мікросервіси. Автор підтвердив збереження попередніх позначень, виділення компонентів і шляхів зв’язків; пропозицію однакового кольору всіх стрілок сам відкликав. Схему в цій ітерації не змінювали.
