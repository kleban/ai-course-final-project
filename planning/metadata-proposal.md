# Метадані наборів даних (опис полів) — пропозиція

Дата: 2026-10-10 (Europe/Kiev), історія 021. Статус: **автор вибрав варіант A (історія 022). Крок 02b без AI реалізовано**; LLM-перетворення — етап 08.

## Що хоче автор (переказ)

До набору даних можна «додати метадані»: завантажити будь-який файл або вставити текст з описом полів. Система перетворює це на чітку структуру: пояснення й людська назва кожного стовпця; для категорійних — можливі значення; для числових — очікуваний діапазон (якщо відомий), одиниці, як пораховано. Відсутнє (наприклад, тип) береться з самого файла даних. Перетворення робить LLM: отримує текст, кілька перших рядків і інструкцію. Питання: чи підходить SQLite, чи потрібна JSON-/документна БД (DuckDB тощо), і чи робити це зараз, пізніше або не робити в MVP.

## Рекомендація коротко

1. **Робити, але у два кроки.** 02b зараз, без AI: скелет опису з даних + ручне редагування + прикріплений сирий опис. Перетворення тексту в структуру через LLM — одразу після адаптера OpenAI (етап 08), до агента (09). Не відкладати поза MVP: опис полів потрібен статистиці (03), вибору цільової змінної в регресії (06), RAG і поясненням агента (07–09).
2. **Сховище — лишити SQLite.** Метадані — це невеликий JSON-документ на набір. SQLite зберігає JSON у колонці (є функції JSON1), дає транзакції разом із журналом і не потребує окремого сервера чи нової залежності. Схему документа контролює Pydantic з номером версії. Окрема документна БД не дає тут переваг, а додає другий файл даних і узгодження між ними.
3. **DuckDB — пізніше і для іншого:** як аналітичний рушій над файлами даних, а не як сховище метаданих. Він доречний, коли знадобляться SQL-запити й з'єднання таблиць (етап 05 «Підготовка й зведення»), інструмент «SQL до даних» для агента (09) або великі файли. Тоді: SQLite — облік (проєкти, набори, метадані, журнал, налаштування), DuckDB — обчислення над підготовленими таблицями pandas; XLSX читає наявний openpyxl/pandas, CSV/Parquet можуть бути файловими джерелами (формат похідних версій ще відкритий), файли — оригінали й похідні версії. Для поточних 20 МБ pandas достатньо.

## Структура метаданих (версія 1)

Документ на набір даних (`dataset_metadata`, JSON):

- `dataset`: назва для людей, опис, джерело (звідки дані, посилання), одиниця спостереження («рядок = квартира»), період/географія, ліцензія або обмеження.
- `columns[]`, для кожного стовпця:
  - `name` (як у файлі), `label` (людська назва), `description`;
  - `kind`: число, категорія, текст, дата, так/ні, ідентифікатор;
  - `unit` (одиниця), `computation` (як пораховано, якщо похідне);
  - для категорій — `categories[]`: значення → пояснення;
  - для чисел — `expected_range` (від–до, якщо відомий; інакше порожньо);
  - `missing_codes` (наприклад, `-1`, `н/д` означають пропуск);
  - `role`: ціль, ознака, ідентифікатор, не використовувати (стане основою вибору змінних для регресії);
  - службове: `source` кожного поля (дані / автор / LLM), `status` (чернетка / підтверджено).
- `observed` — факти з даних, які не редагуються вручну: фактичний тип, мін/макс, частка пропусків, кількість унікальних і до 20 найчастіших значень для категорій. Береться з профілю етапу 02.
- `raw_sources[]` — прикріплені сирі описи: файл (txt, md, csv, xlsx; docx/pdf — пізніше) або вставлений текст; зберігаються без змін поруч з набором.

## Як це працюватиме

**Крок 02b (без AI, можна робити зараз):**
1. Під час завантаження набору автоматично створюється чернетка метаданих з `observed`: тип; категорія, якщо унікальних значень ≤ 20 (список значень); фактичний діапазон для чисел.
2. На сторінці огляду набору — кнопка «Додати метадані»: завантажити файл або вставити текст. Сирий опис зберігається й показується; для txt/md/csv/xlsx текст витягується.
3. Форма редагування опису стовпців (назва, опис, одиниці, роль, діапазон, категорії) і загального опису; кнопка «Підтвердити».
4. Розбіжності між описом і даними підсвічуються: заявлений діапазон 0–100, а в даних є 120; категорія «Інше» описана, але в даних відсутня.

**Крок з LLM (після етапу 08):**
1. LLM отримує: сирий опис, назви стовпців, `observed`, перші 5 рядків і інструкцію (редагований промпт, як інструкції типів проєктів).
2. Відповідь — лише JSON за схемою (structured outputs); перевіряється Pydantic. Помилкова відповідь не зберігається.
3. Результат — чернетка: поля зі `source = LLM`, підтверджені автором поля не перезаписуються. Автор переглядає й підтверджує.
4. Виклик пишеться в трасування (запит, відповідь, токени), як вимагає F-15/F-17.
5. **Приватність:** перші рядки даних ідуть до OpenAI. Перед першим викликом — явне попередження; у налаштуваннях можна вимкнути передавання рядків (тоді лише назви стовпців і `observed`).

## Реалізація 02b (історія 022)

- `src/data_story/metadata.py`: схема документа v1 (Pydantic), скелет із даних, перевірки розбіжностей, `MetadataStore` (чернетка, збереження, підтвердження, сирі описи, витяг тексту з TXT/MD/CSV/JSON/XLSX).
- Відмінності від пропозиції: службове поле `source` ведеться на рівні стовпця (`data` / `author` / `llm`), статус — на рівні документа (`confirmed_at`); збереження без підтвердження знімає підтвердження. Скелет не зберігається, доки автор не натисне «Зберегти». Тип `id` визначається, якщо всі значення текстового стовпця унікальні.
- Схема БД v4: `dataset_metadata`, `metadata_sources`; файли описів — `runtime/projects/<проєкт>/datasets/<набір>/metadata/`.
- API: `GET|PUT /api/datasets/{id}/metadata`, `GET /api/datasets/{id}/metadata/sources`, `POST …/metadata/sources/text`, `POST …/metadata/sources/file`.
- UI: на огляді набору — розділ «Метадані» (статус, попередження, «Додати опис», «Редагувати метадані», сирі описи), таблиця стовпців з назвою, описом і роллю; редактор `/?project=…&dataset=…&view=metadata`.
